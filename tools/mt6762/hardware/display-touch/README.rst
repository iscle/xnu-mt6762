MT6762 display, touch and brightness evidence
===========================================

This package contains portable protocol components, register validators and
an evidence audit. Native consumers are in ``bsd/dev/mt6762_input.c`` and
``bsd/dev/mt6762_display.c``. They require a verified platform handoff and do
not initialize panel power, reset, DSI or touch firmware. They have not been
run on the physical phone. No firmware blobs or captured logs are included.

Components and tests
--------------------

``axs_touch.h`` decodes the stock controller's single 32-byte I2C read at
7-bit address 0x3b on I2C0. It has no register prefix. ``axs_touch_state.h``
tracks five contacts and emits donor-compatible down/move/up values 1/2/3,
with coordinates normalized to 0..65535. Initialize it with the inclusive
Android ABS maxima 384 and 854. Calls must be serialized. Call
``axs_state_expire`` periodically even when no packets arrive, and call
``axs_state_release_all`` before device shutdown/reset. Malformed frames,
duplicate IDs and clock regressions release held contacts. Non-touch status
frames retain state only until the supplied timeout.

``axs15260_panel.h`` contains the extracted DCS commands and a callback
sequencer. Its caller must supply a working DSI transport and delays.
The panel is 384x854, three-lane DSI SYNC_EVENT_VDO_MODE, with PLL_CLOCK=210.
The complete timing, reset and command evidence is generated by the extractor.

Run host tests from this directory::

    sh test.sh

These are synthetic packet/state and register tests, including five contacts,
normalization, missing/up releases, duplicates, malformed input, timeout,
framebuffer bounds, rejected scanout configurations, PWM reserved-bit
preservation and ordered duty/enable/commit writes. They do not establish
hardware operation or physical multitouch performance.

``extract_display_touch.py STOCK_ELF OUTPUT_DIRECTORY`` verifies the exact
stock Image SHA256 before extracting fixed-address facts and the stock display
clock table. The input is a symbolized ELF reconstructed from that Image.
It writes ``facts.json``. Touch firmware extraction is a separate explicit
option; the extracted blob must remain local. The stock driver performs flash
erase/write/read-check, so it must not be treated as a harmless RAM download.

``capture_live.py --adb ADB_PATH --output OUTPUT_DIRECTORY`` reads narrowly
selected metadata through an already authorized ADB connection. It never
requests root, injects input, reads raw registers or writes device settings.
``parse_live_input.py EVENTS_FILE OUTPUT_JSON`` derives evidence from a saved
getevent capture without connecting to a device.

Observed Android evidence
-------------------------

The recorded input file contained 106 lines / 94 events, SHA256
``3240707fc94f775de89f0e608b929a54065339273dd448ab2b8f1de4ff6e9dce``.
Observed volume-up and volume-down down/up pairs came from event0
(``mtk-kpd``); two power-button pairs came from event1 (``mtk-pmic-keys``).
One down/up touch gesture came from event3 (``axs_ts``), with ten positions,
tracking ID0, X=60..152 and Y=290..755. Event5 (``mtk-tpd``) was registered
but emitted no events in this capture. Full-edge coverage and simultaneous
multiple fingers were not observed.

Live driver links identified ``axs_ts`` at I2C0's 0-0038 node (the stock driver
changes the effective address to 0x3b) and ``I2C_LCD_BIAS`` at I2C5/0x3e.
SurfaceFlinger reported 384x854 at 60 Hz. Android brightness was 90/manual,
with light0 color 0xff5a5a5a and display brightness 0.35. Direct framebuffer,
LED sysfs and DT property reads were denied. No privilege escalation was used.
Compositor buffer format/stride do not identify bootloader physical scanout.

PWM sequence and dependencies
-----------------------------

Static DT LED mode5 selects BLS PWM. Stock ELF confirms the PWM update path;
this is separate from the panel's DCS initialization and bias supply.
``brightness-clock-audit.json`` records BSP source hashes, clock dependencies,
addresses and limits. Source paths in that audit are relative to the supplied
``kernel-4.14`` tree; ``facts.json`` is generated by the extractor.

DISP_PWM0 is at 0x1100e000. With exclusive ownership and working clocks/pins
already established, the observed register protocol is:

* Configuration: preserve other bits of CON0 (+0x18), set divider bits25:16;
  preserve other bits of CON1 (+0x1c), set period bits9:0 to1023. The static
  DT requests divider3. Stock config leaves enable unchanged until needed.
* Brightness: clamp to0..1023. For a nonzero value, preserve other CON1 bits
  and set duty bits28:16, then set EN (+0x00) bit0. For zero, set duty1 and
  clear EN bit0, matching the stock zero-duty workaround.
* Commit: write1 then0 to COMMIT (+0x0c), with ordered MMIO/full-system
  barriers as in the stock direct-write path.

The native backend implements only the duty/enable/commit update, after
checking inherited parent3, divider3, period1023 and enabled clocks. It does
not initialize these prerequisites. In particular:

* The DT clock-source request0 maps through the driver to ULPOSC1_D8, whose
  hardware mux encoding is3. Directly writing request0 would select26MHz.
  TOPCKGEN configuration0x80 uses selector bits25:24, gate31 and update19.
* PWM needs its selected parent, TOP mux and infrastructure gate. Display DMA
  additionally needs the DIS power domain, SRAM acknowledgments, bus-protection
  and SMI clamp sequencing, SMI/LARB/GALS clocks, module gates, DSI clocks and
  MIPI reference/PLL/lane setup. A gate write alone cannot establish this state.
* Panel bias is a separate I2C5/0x3e device. Stock init selects bias-enable,
  waits20ms and writes registers0 and1 to0x12. GPIO150 is a static-DT candidate;
  resetGPIO45, touch-resetGPIO174 and touch-IRQGPIO0 also require final-DT or
  physical confirmation. The external backlight IC/output pin remains unknown.
* Preserve a verified LK scanout handoff while implementing these dependencies.
  Historical framebuffer0x7ef90000 is not a current physical address guarantee.
  Panel reinitialization also resets AXS touch and must release active contacts.

Native consumer contract
------------------------

All native fields are under ``/chosen/mt6762-handoff`` with ``version=1`` and
``native-io=1``. Integers are exact-width little-endian ADT values: fields below
are u32 except the four framebuffer address/size fields, which are u64.
The loader must obtain and validate the actual state before asserting any
``verified`` property. The normal QEMU graphics loader does not emit this node.
Its synthetic display remains a separate lab path. A present but malformed
native node causes MiniFB to reject display registration.

Touch requires ``touch-verified=1``, ``touch-bus=0``, ``touch-address=0x3b``,
``touch-max-x=384`` and ``touch-max-y=854``, plus the platform's independently
validated I2C0 prerequisites. The worker issues combined write0x0c/read2,
requires firmware bytes00,07, and then reads32 bytes every8ms. It posts into
``redwood_touch_post`` using the tested state tracker. A100ms deadline releases
stale contacts; transport failure releases contacts and stops, as do eight
consecutive malformed reports. There is no IRQ registration, reset, firmware
upload, automatic restart, or claim that the current phone firmware was read.

Display requires ``display-verified``, ``display-reserved``,
``display-dma-physical`` and ``display-pipeline-verified`` all1. Required layout:

* ``fb-phys``, ``fb-size``, ``fb-reserved-base``, ``fb-reserved-size``: u64.
* ``fb-width=384``, ``fb-height=854``, ``fb-stride``: row bytes, divisible by4.
* ``fb-format=1``: memory bytes B,G,R,A; ``fb-ovl-layer``:0..3 on OVL0.

The base and reservation use16KiB alignment. The range must fit the reservation
and32-bit OVL address space, and hold the visible rows rounded up to16KiB.
The reservation assertion means the loader has excluded it from kernel
allocation, not merely recorded an address. The DMA assertion means the
actual M4U path is bypassed or has a verified identity mapping with ownership
preserved. The current consumer does not configure or independently prove
that translation; a fabricated assertion cannot make a physical boot safe.

The backend reads both DIS power status copies, SRAM/reset/isolation state,
module gates, OVL0 layer/address/pitch/format/geometry, downstream RDMA
direct-link mode, DSI video mode/three lanes/RGB888 and vertical timing. It
accepts only a single unrotated, unclipped BGRA8888 memory layer with opaque
or disabled alpha. MiniFB additionally checks that every mapped console page
and the final byte translate to the same physical framebuffer. Unsupported
handoffs fail rather than reprogramming the display. Early PE initialization
suppresses boot Video whenever any native handoff node exists, retaining UART
output. Only after the later native readback checks pass does the backend
activate the official physical-console mapping path, with IO/write-combined
attributes. The producer must still exclude the reservation and avoid any
conflicting cached alias. No physical boot producer exists yet.

Brightness additionally requires ``brightness-verified``,
``brightness-pins-verified`` and ``brightness-parent-verified`` all1. The
native API ``mt6762_brightness_set(level)`` accepts0..1023. A privileged
``IORegistryEntrySetCFProperty`` on MiniFB with integer key
``MT6762Brightness`` invokes it; out-of-range values or unavailable hardware
return errors. This remains an explicit engineering API. Configuration loss
disables further updates; no PWM writes occur during initialization or failed
validation.

Apple brightness property interface
-----------------------------------

``apple-brightness-abi.json`` records the20F66 binary evidence and Sailfish
reference. CoreBrightness's legacy path calls
``IORegistryEntrySetCFProperties`` on an ``AppleARMBacklight`` service with
``backlight-control=true``. It reads ``IODisplayParameters`` -> ``brightness``
-> ``min``, ``max``, ``value`` and converts its float brightness into an integer
before crossing the kernel boundary. There is no guessed floating-point
user-client selector.

MiniFB now creates this service only when the native PWM getter succeeds.
It advertises0..1023 and the actual inherited duty. ``brightness`` is the
physical integer target, ``FadePeriod`` is a nonnegative signed16.16 duration
in seconds, and optional ``backlight-level`` is logical-level metadata.
Fades run every16ms and retarget from hardware readback. Failed PWM writes stop
the fade; only successfully programmed levels are published. Unsupported
property-only requests and malformed values return errors. Float-origin OSNumber
values are rejected before any integer conversion, including integral-looking
floats. Ordinary lab
graphics does not gain a simulated backlight service.

The original backboardd runs as ``mobile`` and carries boolean entitlement
``com.apple.internal.display-params-access-privileged``. Property writes require
that entitlement or an administrator. Apple executables are unchanged. Host
tests cover integer bounds, negative/oversized encodings,16.16 conversion,
monotonic fades and retargeting. The original framework request path is validated in the synthetic run below.
An actual onscreen slider gesture and physical brightness remain untested.

Remaining work includes current physical handoff evidence and producer,
display DMA translation/cache/reservation proof, panel cold-start and power
lifecycle, brightness UI validation, touch interrupt/suspend/resume, and
real-device validation. QEMU graphics, synthetic I2C and host tests do not
fulfill these items. No physical flash, reset or MMIO write was performed.

Read-only backlight discovery diagnostic
----------------------------------------

``backlight_probe.c`` enumerates both ``AppleARMBacklight`` and the exact
original CoreBrightness matcher, ``IOPropertyMatch`` containing boolean
``backlight-control=true``. It prints class conformance, registry ID and the
brightness dictionary. It makes no property changes. Build with an iOS
cross compiler and SDK, linking ``CoreFoundation`` and ``IOKit``; for example::

  xnu-clang -arch arm64 -isysroot "$THEOS/sdks/iPhoneOS16.5.sdk" -O1 \
    -Wall -Wextra -framework CoreFoundation -framework IOKit \
    -o /new/backlight_probe backlight_probe.c

Include the resulting project helper in the separate laboratory root image
and invoke ``/redwood/bin/backlight_probe 12`` through its existing job list.
Twelve iterations take approximately110seconds; the default is one iteration.
A helper installed in that image is not at ``/bin`` in the iOS system root.

The Apple CADisplay discovery path and legacy fallback both use this property
matcher. ``AppleARMBacklight`` conformance identifies the built-in display;
``kUSBContainerID`` is optional. No additional properties should be invented
without evidence. First-eight kernel entry/rejection logs distinguish missing
requests from requests rejected by unchanged ABI/authorization checks.

Original BackBoardServices laboratory request
---------------------------------------------

``backlight_request.c`` calls the original20F66 framework exports recorded in
``apple-brightness-abi.json``. It sends logical levels0.25 and0.75, then restores
the initial logical level. It never calls the direct engineering property API.
It requires ``--qemu-lab`` plus the synthetic ADT contract and refuses an absent
contract. Build with the same SDK and frameworks as ``backlight_probe`` and sign
only this project helper with ``backlight_request.entitlements``::

  xnu-clang -arch arm64 -isysroot "$THEOS/sdks/iPhoneOS16.5.sdk" -O1 \
    -Wall -Wextra -framework CoreFoundation -framework IOKit \
    -o /new/backlight_request backlight_request.c
  ldid -Sbacklight_request.entitlements /new/backlight_request

Install it in the separate laboratory root and run::

  /redwood/bin/backlight_request --qemu-lab 45 4

The optional numbers are initial delay and per-target hold seconds. For a
late GUI test, a longer hold can span SpringBoard startup; availability alone
does not prove the display is unlocked. The helper's ``native`` observation
reads the last confirmed published duty. It is not a fresh hardware register
read. Require independent QEMU PWM commit counters and original ``backboardd``
request logs before attributing a change to the original Apple path. Apple idle
policy can legitimately supersede a requested level before the next sample.

The discovered ``DisplayBrightness``, ``brightness-nits``,
``brightness-nits-cap`` and slider-position metadata do not establish a nits to
PWM calibration. They remain unsupported as standalone native requests. The
original legacy integer target and authorization checks stay in effect.

``original-bks-build13.json`` records the completed220-second synthetic test.
Original ``backboardd`` delivered integer targets256,768,1 and512. The helper
observed last-confirmed published levels256,1 and512; Apple idle policy
superseded0.75 before that sample. Independently, QEMU recorded16 PWM register
writes, four commits, zero rejected writes and restored duty512. Its20-second
samples did not capture intermediate levels, so they prove commit activity and
restoration rather than each transient target. This proves the original Apple
framework request path reaches the native backend in the model. It does not
prove a physical panel response or an onscreen brightness slider gesture.

Inherited-display blank and wake
--------------------------------

``display-power-abi.json`` records original QuartzCore/IOMobileFramebuffer
selector12: one boolean scalar for display on. With a native handoff, MiniFB
requires the original display entitlement or administrator. Off serializes
against framebuffer copies, cancels any fade, saves actual confirmed PWM duty,
and programs/readbacks zero. Queue completions and VBL notifications continue;
subsequent swaps are consumed without copying into framebuffer RAM. The panel
continues scanning the inherited last frame with its backlight disabled.

Valid brightness requests while blank update only a separate desired target
and duration. Published actual brightness stays zero. Repeated off preserves
the pending request. Wake restores the saved confirmed level, or applies the
latest pending request through the normal readback/fade path, then permits
framebuffer copies. Faults and service stop remain terminal. The engineering
property shares this workloop, so it cannot bypass lifecycle gates. Lock order
is framebuffer lock, backlight workloop, then native PWM mutex; the backlight
never acquires the framebuffer lock. Default non-native graphics is unchanged.

This is not DSI panel sleep or clock/rail suspension. Stock DCS suspend and
proximity-preserved resume commands are known, but safe command transport,
normal resume power/reset ordering and physical validation remain outstanding.
No panel sleep commands are issued by this implementation.

Build the project probes with ``../build-probes.sh`` using explicit ``IOS_CC``,
``IOS_SDK``, ``LDID`` and a new output directory. The QEMU-only
``display_power_probe --qemu-lab 45`` uses original IOMobileFramebuffer power
calls and original BKS brightness calls to test off, deferred target, repeated
off and wake. Install it under ``/redwood/bin`` and run it separately from
``backlight_request``. Sample independent model PWM state at one-second
intervals; helper registry observations alone are not a hardware trace.

The180-second build16 test in ``display-lifecycle-build16.json`` completed
without a panic. Original framework calls produced256 -> off0 -> wake1 ->
restore512. While blank, CoreBrightness queued768 then superseded it with its
idle target1; duplicate off preserved1. Nine independent one-second QEMU
samples held applied0 and commit count2 throughout the blank interval. Wake
and restore brought the total to four commits/16 writes with no rejected
writes. Model applied0 uses EN0 with stored duty1. This validates pending-target
and PWM lifecycle behavior; it does not independently measure framebuffer-copy
suppression or establish physical DSI/panel sleep.

Panel sleep transport investigation
-----------------------------------

``panel-lifecycle-audit.json`` separates the exact normal panel power cycle
from the proximity branch. Normal suspend sends display-off/sleep-in, waits
an additional120ms beyond the table delays, then disables GPIO150 bias. Normal
resume includes bias programming, an AXS touch reset, panel reset and the full
vendor initialization table. Proximity-enabled suspend skips sleep commands
and bias shutdown entirely; its short resume table is not proof of wake from
sleep with retained bias.

Exact stock also stops the display path before panel suspend. Its DSI stop
switches to command mode, waits idle and disables the HS clock. Consequently,
sending sleep while inherited video scanout continues would be a new operating
sequence requiring separate panel evidence.

``mt6762_dsi_vm_core.h`` is an unwired, host-testable short-command transport
for an already configured video-mode command facility. It supports only the
four recovered short DCS commands with parameter00. An external admission
callback must verify exclusive DSI/GCE/IRQ ownership and initialized physical
state; this file provides no native ownership implementation. It changes only
VM packet content, the VM trigger and its completion status. It uses the
stock-corroborated write-zero-to-clear status semantics, observes fresh
completion with bounded polling, and latches faults without automatic reset
or retry. Other clocks, modes, rails, interrupts and scanout remain untouched.

The corresponding synthetic test checks packets, trigger ordering, unrelated
status preservation, stale completion, timeout and terminal faults. Controller
completion does not acknowledge physical panel state. This transport is not
wired into the working PWM/copy lifecycle and does not implement panel sleep.

First-command admission is separate from ownership. The prototype requires an
``admit_initial_idle`` callback backed by a verified idle handoff/drain; no
physical implementation is supplied. It rejects an inherited high VM trigger
before any writes, even if stale DONE is also high. Low START alone is not
idle proof. A retained high trigger is accepted only after this transport's
own command completed and final acknowledgement was read back cleared, with
unchanged prior packet and no unexpected new DONE. Dropped final acknowledgement
fails terminally. Tests cover inherited pending commands, absent idle proof,
dropped final acknowledgement and invalidated retained-completion state.
